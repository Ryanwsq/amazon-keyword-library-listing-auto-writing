# Project task architecture

本仓库只服务 Amazon 关键词词库项目。采用一个长期主任务和多个长期单一职责副任务；副任务不会因一次运行结束而删除，也不与永久 Git 分支绑定。

## Logical hierarchy

```text
Amazon关键词词库｜主任务｜main
├── SIF竞品反查｜副任务｜main
├── Amazon联想采集｜副任务｜main
├── 卖家精灵扩词｜副任务｜main
├── 关键词清洗｜副任务｜main
├── 词频统计｜副任务｜main
├── 关键词分类｜副任务｜main
├── 竞争性分析｜副任务｜main
├── 趋势性分析｜副任务｜main
├── 最终工作簿装配｜副任务｜main
└── 独立质量验证｜副任务｜main
```

## Main task

主任务负责用户输入、运行版本、依赖调度、三来源机械合并、阶段完成门、跨模块冲突、最终验收、问题台账和用户交付。主任务不执行来源、清洗、词频、分类、竞争、趋势、装配或独立质量模块，也不得因副任务不可用、未初始化、操作不便或已能看到证据而代跑。副任务不互相传递正式结论，所有结果统一回传主任务；数据量大的来源副任务先在自己的Run目录装配最小工作簿，只回传路径、哈希、数量、状态和异常摘要，不把长响应正文复制进主任务消息。

只有用户在了解受影响模块、证据状态和验收影响后明确批准的一次性Run例外，主任务才可接收已经产生的证据。例外必须写入本机问题/运行清单，不得成为默认路由、长期授权或P1能力证据。

主任务拥有 `PROJECT.md`、项目级决策日志、知识索引、端到端流程和任务架构。用户确认真实验证问题后，主任务再把单一模块的 Skill/知识迭代交回对应长期副任务。

## Persistent side tasks

每个副任务长期负责一个执行模块，以及该模块对应的 Skill、直接引用合同和模块知识。一次运行结束后任务保持可继续使用；下一次由主任务发送新的 `Run_ID`、输入版本、允许动作和验收标准。

十个单一职责长期副任务已在本设备的独立 Codex 项目中创建，目标 Skill 包均已通过仓库 P0并建立三个证据登记槽位；实际任务 ID、路径和授权状态只写入被忽略的本机映射，换设备时按逻辑角色重建。每次正式派发前，主任务必须把本机映射与当前Codex任务列表机械核对，只有逻辑角色、固定标题、Task ID/host、执行cwd、Run、revision和输出目录全部匹配时才可下发；实际值不得进入tracked文件或交付物。三来源机械合并和第一板块两Sheet总门继续由主任务负责，不建立第四个来源副任务。

副任务有两种互斥模式：

1. `read-only validation`：只读取锁定的 Skills 和知识，业务文件写入本机忽略目录；不得修改仓库规则。
2. `approved iteration`：用户确认问题后，只修改该副任务拥有的 Skill、合同和模块知识，再回传主任务整合。

## Execution dependency

每个Run先在本机忽略目录建立内容寻址run contract并并行完成SIF/卖家精灵无凭据登录preflight。每次派发除固定任务身份门外还必须核对stage key；完成回传必须包含输出/证据哈希、人口和状态。规则、输入、依赖或执行器版本漂移时只重跑受影响阶段及后代，无依赖关系分支不被技术失败冻结；最终装配汇合门不变。

```text
主任务从三组开头输入锁定真实输入；产品基础信息已包含目标Amazon类目及是否存在多个稳定产品类型细分
→ 原始竞品ASIN超过5个时主任务先按稳定产品类型每类保留输入顺序中的第一个有效ASIN
→ SIF竞品反查（首次官网查询前检查登录；未登录只回传主任务awaiting_login）
→ 主任务依据事实卡与SIF证据独立确认一级品类核心，并仅在类目有多个稳定产品类型细分时确认可选细分核心、完成目标细分简称/紧凑表达强等价闭环，再锁定主锚点、联想锚点与卖家精灵一至两个种子
→ Amazon联想 与 卖家精灵扩词并行（卖家精灵查询前检查登录；每个种子只做一次成功完整导出）
→ 主任务机械合并三来源
→ 关键词清洗并闭合通用词库资格
→ 资格纳入词频统计 与 完整人口关键词分类并行
→ 资格纳入人口竞争性分析 与 趋势性分析并行
→ 最终工作簿装配
→ production：最终装配完成Gate 1–20，Gate 21=not_applicable，直接交付
→ test-validation：独立质量验证（普通测试compact-validation；变更/P1案例/异常full-regression；均保留21项门和完整风险人口）
→ 主任务验收与交付
```

## P1 case validation

独立仓库准备完成后，第一次正式运行必须使用用户提供的真实案例和固定仓库版本。验证期间不修改 Skills、知识、端到端流程，不更新飞书，不升级 maturity；所有原始数据、工作簿、预览和问题候选写入 `.local/runs/<Run_ID>/`。

验证完成后先由主任务交付文件和问题台账。只有用户逐项确认修改方向后，长期副任务才进入 `approved iteration` 更新各自模块。P1案例固定为`run_type=test-validation`并使用`full-regression`；普通production不调度独立质量验证，也不能替代两个正常加一个边界案例的完整回归证据。

每个Skill的`evidence/index.md`固定登记两个正常案例和一个边界/异常案例。索引不是P1证据，正式只读运行期间不得更新；一个端到端Run只为实际执行到的Skill各贡献一个独立模块候选。Run结束、用户确认且进入获准发布批次后，才写入脱敏案例文件并更新登记状态，历史运行不得追认。

## Local identity

仓库跟踪逻辑角色和标题，不跟踪实际 Codex 任务 ID。真实任务 ID、绝对路径、当前 Worktree 和授权状态只写入被忽略的 `thread-map.local.md`。换电脑时从逻辑角色、仓库相对路径和最新交接重建映射。

## Git isolation

长期任务不是长期分支。`main` 是唯一长期基线；获准的仓库写入使用短期分支。多个副任务同时修改跟踪文件时使用独立 Worktree，且不得同时修改同一 Skill、知识文章或端到端流程。
