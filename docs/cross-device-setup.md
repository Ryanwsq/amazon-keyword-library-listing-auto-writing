# 跨电脑首启与本地统一入口

本文件只管理安装、路径、外部能力与可用状态，不替代两个项目的AGENTS、Skill、业务判断边界或人工门。README中的来源优先级摘要以相应拥有合同为准。站点映射、来源路由和字段导航统一见[全流程输入输出与来源路由索引](workflow-input-output-and-source-routing.md)。

## 一个仓库，不复制本机身份

统一克隆总仓，并只把总仓目录添加为一个 Codex 项目。关键词模块入口为`projects/amazon-keyword-library`，Listing模块入口为`projects/amazon-listing-pipeline`；两个子目录不需要分别成为已保存项目。Listing `main` 是整条流程的统一入口，关键词 `keyword-main` 仍拥有关键词子流程与固定副任务。显式关键词单项目任务继续使用原独立入口，不新增 Listing 依赖。所有新目标任务从这份代码或它的受控 Git 工作树取版本。

应用侧栏中的“已保存项目”、现有任务的 cwd 和浏览器会话不会被 Git 自动修改。文件合并不等于任务绑定迁移。旧项目、旧任务和原文件保持原样；新目标的角色清点必须限定目标项目，不能用旧项目同名任务充数。已有目标任务先核对复用；只有用户明确授权创建缺少角色时才创建，不迁移聊天归属、不手工篡改应用内部数据库、不删除旧项目。任务创建成功、只读装载成功和业务 READY 分别记录。

每个目标任务分别记录实际 app cwd、显式 `execution_project_root`、`git_root`、Git revision 与所属包路径/version/manifest 哈希。模块命令使用明确的业务项目工作目录，Git 命令明确指向其 Git 根；不能因为默认 cwd 仍在旧工作树就执行旧规则，也不能把映射文件视为沙箱写入授权。需要写权限时按当前客户端审批机制处理，不能静默改用另一份旧代码。

旧输入、真实工作簿、历史Run、任务记录和登录信息保留在原本机位置。新电脑需要使用某份历史词库时，必须另行获准传输、核对来源与哈希、执行既有复用规则；干净克隆不含这些私有文件，也不能自动补造。

## 首次启动顺序

1. 克隆后在总仓根运行README中的环境预检及统一校验。Python预检只探测本机运行时，不访问提供商、不读密钥；系统`python3`低于3.11时，先安装/配置3.11+，或在Codex任务中发现并使用该电脑实际提供的工作区Python重新运行，不复制另一台电脑的绝对运行时路径。Windows使用短目录，避免将总仓放进深层同步盘路径；不能移动单个角色包文件来缩短路径。
2. 在执行任务的环境中准备可用的表格生成、重新加载、公式检查和渲染能力。部署不能删除渲染、隐私、哈希或人口检查来“适配”缺少依赖的电脑。`unzip`是现有装配审计脚本的真实外部依赖；预检失败时先安装兼容版本，不能仅用7-Zip图形界面存在来代替命令兼容性。
3. 列出目标项目已有任务并逐个核对角色、项目归属与状态。获明确创建授权后才补齐缺少角色；当前完整清点为 Listing 10 个（1 总控、7 业务、2 接收）及关键词 11 个（1 主任务、10 长期副任务）。未明确授权时报告缺少项并停止创建，不拿旧项目同名任务或索引占位当作已存在目标。
4. Listing读取其`task-packages/registry.json`，以角色、版本、包路径和manifest哈希明确绑定；每个角色完整读包内`AGENTS.md`、`Agent.md`、`LOAD_ORDER.md`及全部规定依赖/知识正文。关键词各角色完整读取项目AGENTS与必读资料，再按`docs/thread-architecture.md`和`docs/thread-roles.md`加载所属 Skill。参照关键词`docs/thread-map.local.example.md`建立新的本机映射，不覆盖旧 Listing 映射。真实ID、host、cwd和授权只保存在 Git 忽略文件中。注册表里的冻结发布标签是历史封包属性，不是当前GitHub在线状态；不为安装改冻结哈希，不把`dependencies/skills/`注册成额外执行角色。每个任务必须返回实际读取与包校验回执，不能复制旧加载状态。
5. 按README准备网站账号、MCP及浏览器能力，在实际拥有任务中预检。完整输入后必须先显示由输入导出的站点摘要；Amazon-US为`amazon.com/10001/Alexa/英语`，Amazon-DE为`amazon.de/80539/Rufus/德语`。随后立即按总控固定八会话矩阵引导用户准备登录：六个Amazon拥有任务由用户逐任务手动登录；SIF和卖家精灵拥有任务按输入模板`登录准备`中的非敏感账户别名/凭据引用使用浏览器已保存凭据或本机密码管理器。每份回执绑定Task/host/dispatch，全部完成后才允许业务动作。新电脑没有对应本机凭据条目或Amazon会话时保持待登录，Git不会迁移秘密。若关键词挖掘默认打开Sorftime官网，或任一任务进入了非锁定站点，立即停止并核对当前注册角色包、cwd和站点路由。Windows上的浏览器备用只在各模块原有合同允许的范围使用，不跨模块扩大备用权限。
6. 汇总角色清点、侧栏可见性、实际已读回执、包哈希、环境缺口和当前 Git 状态。侧栏中暂时看不到任务时先通过任务清单核对真实项目归属、Task ID、host和cwd，不直接当成任务不存在并重复创建。由用户指定的验收拥有方复核业务文件保全、角色职责与跨模块输入输出；安装任务的完成回执不能替代独立验收。初始化不启动业务。新 Run 前重新锁定当前 Git revision、规则哈希、三组输入、marketplace、产品事实和输出目录，校验角色/任务/cwd；输入版本与执行 Git 版本分别保留。跨项目沿用现有交接合同、双 Run 与来源哈希、正式回执和 Listing 主任务 READY 权限；两道人机门不变，旧事实不得覆盖新事实，旧任务 ID 不得复制成当前身份。

## 环境检查的含义

- `check_environment.py`：Python、Git、Node、ZIP命令兼容性和公开文件的Windows路径风险；不安装、不修复、不读账号配置。ZIP探针只在系统临时目录生成并删除合成样本，不读取用户工作簿。
- `validate_projects.py`：精确发布清单、22个权威Skill、两个项目原有结构/依赖/角色包检查。源文件缺失、多出未审查文件或字节漂移都失败，不能重新封存哈希来绕过。
- 明确忽略的本机绑定、`.codex/`、`.env*`及系统生成的`.DS_Store`/`Thumbs.db`不是发布输入；检查器不读取它们，也禁止将它们登记进发布清单。其他未审查业务文件仍失败。已获准发布的模板仍按原始哈希核验，不按扩展名跳过。
- 这两项通过仅证明所覆盖的本机机械条件；不证明网页登录、MCP剩余额度、Alexa可访问、业务语义正确或P1。
- Mac上的`core.autocrlf=true`干净克隆只是Windows换行配置模拟，不是Windows全流程实测。真实Windows环境须另行通过安装预检、浏览器/表格能力检查及获准业务验证。

## 可复制到新电脑的初始化请求

在Codex打开已克隆的总仓后，用户可主动发送下面的请求。此段只是供用户选择的请求模板，文档本身不授予创建任务或启动业务的权限。

> 请在我已添加的这个总仓 Codex 项目中完成只读初始化。先完整读取根 AGENTS 和两个模块各自规定的入口资料，运行本机环境与结构检查，列出目标项目现有任务并核对角色/版本。我明确授权创建目标项目缺少的完整 Listing 10 角色（含总控、7 个业务、2 个接收整理）及关键词主任务和10个长期副任务；已有目标任务核对后复用，旧项目及其任务和历史文件保留，不跨项目凑数或重复创建。Listing 总控是整体流程入口，关键词主任务管理独立子流程，任何主任务均不得代跑业务模块。每个角色按其架构/当前注册包完整读取并返回真实装载回执。实际ID、host、app cwd、业务执行根、Git根、包路径/version/hash和本机权限仅登记在新的 Git 忽略映射中，不覆盖旧映射或修改稳定 Skill、知识、判断边界和冻结包。列出待登录网站、待配置 MCP 和缺少的表格/浏览器能力，不读取密钥、不调用付费业务接口、不抓取产品或重跑历史输入。初始化不发业务 READY、不代我确认 Listing 两道人机门。最后分别报告文件保全、角色创建/实际加载、环境/登录及待验收项；存在阻塞不得宣称业务可开跑。

初始化后，用户再提交本轮三组输入和运行授权。Listing仍保留其原合同中的确认门；关键词生产/测试路由也仍按原规则，不因安装模板改变。

## 后续更新

先检查当前工作树有无未提交修改或运行中任务；有则先保全并协调，不自动覆盖。更新日常`main`只允许快进，之后重新运行两项检查，并在新Run开始前刷新版本锁。原始Run和冻结成果不可就地改写。2026-09-04德国站验证维护已更新marketplace路由、网页登录门、分阶段来源优先级及相关业务Skill/合同；更新后的下一次能力验证必须标记为`test-validation + full-regression`，不得把安装检查或本次已结束且跳过人工QA的Run回写为P1通过。
